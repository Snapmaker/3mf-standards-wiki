## B. 机制确认：版本号、命名别名、时间戳

### Q6. `project_schema_version` 的维护规则（P0）

**背景**：源码 `src/libslic3r/ProjectSchemaVersion.cpp` 已有格式版本注册表：`project_schema_version`，current_version = 1、legacy_version = 1，提供 `version_from(config)`（缺失时视为 legacy）与 `is_newer(config)`。但仅 2.4.0 样本落盘该字段，2.3.6 文件缺失——读取端只能依赖"缺失 = legacy"的隐式约定。

**问题**：
1. 版本号何时递增？谁维护？有无变更记录？
2. "缺失 = legacy"是否可靠——是否存在写了版本号但仍走 legacy 路径的情况？
3. 规范拟将其升级为**强制 header 字段**并定义递增规则（对齐语义化版本 Minor/Major），写入端配合成本如何？

**期望产出**：版本机制说明 + 对强制化的意见。这是规范"版本元数据"章节的核心。

### Q7. 预设 `version` 字段的语义（P1）

**背景**：嵌入预设 header 的 `version`（实测 2.3.0.4 / 2.5.0.66 / 2.6.0.51）与软件版本（2.3.6）互不相干，三套版本号无文档说明（W8）。

**问题**：预设 `version` 是什么（生成该预设的上游软件版本？）？读取端是否使用它做分支判断？

**期望产出**：语义说明。供规范统一叙述三套版本号（软件版本 / 预设版本 / 文件 schema 版本）。

### Q8. 30 个序列化别名的维护机制（P1）

**背景**：31 个"落盘但无静态定义"字段中 30 个是序列化名 ≠ 定义名：`filament_retract_*` / `filament_wipe*` / `filament_z_hop*` 等 18 个（源码定义为 `retract_*` 族）、`machine_max_{acceleration,jerk,speed}_{x,y,z,e}` 12 个（机器限制项，另行定义）。

**问题**：
1. 别名映射在代码哪里维护？是序列化层硬编码列表吗？
2. 新增参数是否有统一的别名机制，还是逐个处理？

**期望产出**：映射代码位置 + 机制说明。规范将正式登记这 30 个别名并定义命名规则，防止新参数继续产生隐性别名。

### Q9. ModelConfig timestamp 的语义（P2）

**背景**：《Config 配置系统分析》提及 ModelConfig 带 timestamp（局部配置时间戳），语义未明，疑与增量切片或编辑历史相关。

**问题**：timestamp 的用途是什么？目前是否写入 3mf？是否应该写入？

**期望产出**：语义说明。决定规范是否为局部配置时间戳留位。

### Q10. 2.4.0 新增 8 字段的定义位置（P1）

**背景**：`filament_flow_step_size`、`filament_flow_support`、`filament_grouping_mode`、`filament_volume_type`、`nozzle_volume_type`、`printer_flow_support`、`process_flow_support`、`project_schema_version` 在 2.4.0 样本首次出现；当前手头 2.3.x 源码的 `PrintConfig.cpp` 未见静态定义（`project_schema_version` 除外）。

## E. 补充问题（2026-10-15：立方体对照样本实测）

**背景**：新增两个对照样本——`Downloads/立方体1.3mf`（直接保存工程）与 `Downloads/立方体2.3mf`（菜单 Export Generic 3MF 导出），同一工程、同一软件（Snapmaker_Orca-2.4.0）的两次导出。逐一 MD5 对比结果：**Metadata/ 下 8 个公共文件字节级完全相同**，差异全部集中在 3D 几何层：

| 维度 | 立方体1（直接保存） | 立方体2（导出通用） |
|---|---|---|
| 包内条目数 | 15 | 11 |
| 网格存储 | 外拆 `3D/Objects/<对象名>_<obj_id>.model`（每对象一文件） | 内嵌 `3D/3dmodel.model` |
| `3D/_rels/3dmodel.model.rels` | 有（登记 3 个外部部件） | 无 |
| 生产扩展 + UUID | 有（`requiredextensions="p"`，对象/组件/实例全带 UUID） | 无（xmlns:p 未声明） |

源码锚点：直接保存走 `Snapmaker_Orca.cpp:6298`（strategy 含 `SplitModel|ShareMesh|UseLoadedId`）；通用导出走 `Plater::export_core_3mf`（Plater.cpp:20414，strategy 仅 `Silence`），菜单 tooltip 自述 "Export 3mf file without using some 3mf-extensions"（MainFrame.cpp:2638）；外拆条件 `bbs_3mf.cpp:6493`，文件名生成 `bbs_3mf.cpp:6662`。

### Q21. 通用导出的清洗范围（P1）

**背景**：菜单语义是"去掉 3mf 扩展、便于第三方软件读取"，但实测清洗只发生在 3D 几何层（去生产扩展/UUID/外拆网格）；`Metadata/` 全套配置（project_settings 584 字段、model_settings、4 张盘缩略图）**字节级原样带出**。第三方拿到"通用"文件等于拿到完整切片工程配置——包括 W2 泄漏字段（`inherits_group` 等）、Q14 的预设元数据污染，以及 Q11 待裁决的凭据字段面。

**问题**：
1. 通用导出保留完整 Metadata 是有意设计（如回导入需要）还是清洗未覆盖到此层？
2. 规范拟要求通用导出剥离 `Metadata/` 配置层（或仅保留几何引用必需项），是否符合预期？

**期望产出**：清洗范围结论。与 Q14（导出清洗规则）合并裁决，共同构成规范"导出形态"章节。

### Q22. 外拆对象文件名的安全性（P2）

**背景**：外拆网格文件名 = `<对象名>_<obj_id>.model`，`obj->name` 直接拼接、**写入前无任何清洗**（bbs_3mf.cpp:6662）。对象名是用户输入：实测出现中文名（`3D/Objects/立方体_1.model`）；对象名含 `/`、`\`、Windows 保留字符或超长时，zip 条目名层面的行为未定义（路径穿越/编码/跨平台解压风险）。对照：Bambu 原生文件用与对象名解耦的安全名（`object_1.model`）。

**问题**：

2. 规范拟将外拆文件名与对象名解耦（固定模式如 `object_<obj_id>.model`，对象名只存 model_settings），写入端配合成本？

**期望产出**：处置方向。影响规范"包内条目命名"章节。
